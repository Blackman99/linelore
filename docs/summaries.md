# Summaries (`--summarize`)

linelore prints facts: the commit, the PR or MR, the issues it closed, the review comments. Sometimes you want one sentence instead of reading all of them. `--summarize` hands those facts to **a model command you already use** and prints its answer underneath, labelled as what it is.

Off by default. linelore has no model, no API key and makes no network call for this; it runs your command and nothing else.

```console
$ linelore src/requests/utils.py:795 --summarize-cmd 'ollama run --nowordwrap qwen2.5:1.5b'
src/requests/utils.py:795  value_changed = value is not None
  commit  1d7fd6c8b3  2017-06-06  mlcrazy
          Fixes error swallowing in set_environ
  PR #4134  Raise exceptions in utils.set_environ  (@mlcrazy, merged 2017-06-09)
          https://github.com/psf/requests/pull/4134
  …
  review  @nateprewitt (line 621): @Lukasa what are your thoughts on adding `value_changed = value is not None`, …
  review  @Lukasa (line 621): Works for me!

Summary (generated by ollama, may be wrong; not checked by linelore)
  The code at line 795 in `src/requests/utils.py` adds a condition to the `value_changed` variable based on whether `value` is `None`. This change was made by @mlcrazy in commit 1d7fd6c8b3, fixing an error that occurs when the `set_environ` method is called with `value` set to `None`. … The code review from @Lukasa also addressed the use of `None` in the `get` method and proposed a cleaner way to handle the `value_changed` condition, which @nateprewitt agreed with.
```

That is a real run with a small local model (Qwen2.5 1.5B through ollama, on CPU; trimmed where marked …). Look at its last sentence: it has the review backwards. @nateprewitt proposed the single `value_changed` check and @Lukasa agreed, as the facts right above it say. That is why the summary sits below the facts with a label, and why linelore never feeds it back into them.

## Set it up once

Any command that reads a prompt on stdin and prints an answer on stdout works:

```bash
export LINELORE_SUMMARIZE_CMD='llm -m gpt-4o-mini'        # simonw/llm
export LINELORE_SUMMARIZE_CMD='ollama run --nowordwrap qwen2.5:1.5b'  # local, nothing leaves the machine
export LINELORE_SUMMARIZE_CMD='claude -p'                 # Claude Code, print mode
export LINELORE_SUMMARIZE_CMD='my-company-llm --no-stream'
```

Then ask for a summary when you want one:

```bash
linelore src/app.py:42 --summarize
linelore src/app.py:10-30 --summarize --json
```

Setting the variable alone never runs anything; you still pass `--summarize` each time. `--summarize-cmd CMD` sets the command for one run and implies `--summarize`.

The command is split like a shell would split it (quotes work) but is **not** run through a shell, so pipes and `$VARS` inside it are not expanded. Wrap anything fancier in a script.

## What your command receives

On stdin, UTF-8: a short instruction, a separator line, then linelore's plain-text output (no colour, no wrapping):

```text
Below is what linelore found for a line of code: the commit that last changed it, the pull request (or merge request) that merged it, the issues it closed and review comments near the line.
In 2-4 sentences, explain why the code is the way it is. Use only these facts and cite them (#PR, #issue, @reviewer). If they don't explain the reason, say so plainly. Do not guess.

--- linelore output ---
src/cart.py:42  total += round(item.price * item.qty, 2)
  commit  3f9c2a71be  2024-05-06  Mei Chen
  …
```

`LINELORE_SUMMARIZE_PROMPT` replaces the instruction (for another language, a different length, your own rules). Set it to an empty string to send only the separator and the facts, e.g. when your command has its own system prompt.

That text includes the blamed line, PR and issue excerpts and review comments. It goes wherever your command sends it: nowhere, for a local model.

## How it is labelled

- **Terminal:** the facts print first, exactly as without `--summarize`. Then a blank line and `Summary (generated by NAME, may be wrong; not checked by linelore)`, then the answer, indented. NAME is only the program name, never its arguments, so a key passed as a flag doesn't end up in your scrollback.
- **JSON:** every fact field is identical to a run without `--summarize`. The answer is one extra top-level field, never mixed into `pulls`, `issues` or `notes`:

```json
"model_summary": {
  "by": "llm",
  "text": "The flag exists because a reviewer asked …",
  "error": null,
  "disclaimer": "Generated by a model command you configured, from linelore's facts. It may be wrong; it is not one of linelore's facts."
}
```

The answer is cleaned before it is shown: terminal escape sequences and control characters are removed and it is capped at 4,000 characters. CLIs that re-wrap a streamed answer by moving the cursor back over a half-printed word (`ollama run` does) are replayed, not just stripped, so you don't get `bu` / `bug` at every line end; `--nowordwrap` avoids the issue in ollama altogether.

## When it goes wrong

The facts are always printed; only the summary is skipped. linelore says why on stderr and exits with **4**:

| What happened | Message |
|---|---|
| `--summarize` but no command | usage error (exit 2) before anything runs: pass `--summarize-cmd` or set `LINELORE_SUMMARIZE_CMD` |
| command not installed | `` `llm` (from LINELORE_SUMMARIZE_CMD) is not installed or not on PATH `` |
| command fails | `` `llm` exited with status 1: `` plus the last lines of its stderr |
| too slow | `` `llm` gave no answer within 120 s, so linelore stopped it `` (the whole process group, so wrapper scripts don't linger) |
| no output | `` `llm` printed nothing on stdout `` |

With `--json`, the same message is also in `model_summary.error` (and `text` is `null`).

`LINELORE_SUMMARIZE_TIMEOUT` sets the wait in seconds (default 120; local models on a laptop can be slow). Ctrl-C stops the command too.

## Why it works this way

linelore's [goal](https://github.com/Blackman99/linelore/blob/main/GOAL.md) rules out "LLM-generated guesses presented as facts". So the summary is opt-in per run, comes from a model you chose, is labelled every time it is shown, sits apart from the facts in both outputs, and never changes them. If the PR thread doesn't say why, a good prompt makes the model say that too.
